# Utilities & Helpers Documentation: IoT Copilot AI

This document catalogs the utility functions (often called "helpers") used across both the client and server. Utilities are pure, stateless functions that solve specific, isolated problems without side effects.

---

## Client Utilities (`client/src/utils/`)

### 1. `cn.ts`
- **Purpose:** Merges Tailwind CSS classes intelligently.
- **Problem solved:** Prevents style conflicts when passing custom `className` props to reusable components (e.g., passing `bg-red-500` to a button that natively has `bg-blue-500`).
- **Dependencies:** Relies on `clsx` (for conditional classes) and `tailwind-merge` (for conflict resolution).
- **Usage:** Used in almost every single UI component.

### 2. `date.ts`
- **Purpose:** Standardizes date parsing and formatting.
- **Problem solved:** MongoDB stores dates as ISO strings. The UI needs to display them as "2 days ago" or "Jan 14, 2024". 
- **Business Logic:** Wraps the native `Intl.DateTimeFormat` or a library like `date-fns`/`dayjs` to ensure timezones are handled consistently on the client side.

### 3. `format.ts`
- **Purpose:** Generic data formatting.
- **Problem solved:** Formats numbers (e.g., turning `1500` into `1.5k`), currencies (for component budgets), or strings (truncating long project descriptions with ellipses).

### 4. `validation.ts`
- **Purpose:** Client-side Zod schema definitions.
- **Problem solved:** Centralizes form validation rules (e.g., "password must be 6 chars", "email must be valid").
- **Who uses it:** Imported by React Hook Form inside components like the Login or Project Creation forms.

## Server Utilities (`server/src/utils/`)

### 1. `logger.ts`
- **Purpose:** Standardized backend logging.
- **Problem solved:** Prevents the use of raw `console.log`, which lacks severity levels and timestamps.
- **Business Logic:** Likely wraps a library like `winston` or `pino`, or simply provides formatted `console.info`, `console.warn`, and `console.error` wrappers with ISO timestamps.

### 2. `errors.ts`
- **Purpose:** Custom error classes.
- **Problem solved:** Provides specific Error sub-classes like `NotFoundError`, `UnauthorizedError`, or `ValidationError`.
- **Usage:** Controllers throw these errors, and the central `errorHandler` middleware catches them to format the correct HTTP status code.

### 3. `constants.ts`
- **Purpose:** Centralized "magic strings" and "magic numbers".
- **Problem solved:** Prevents hardcoding values like `MAX_PROJECTS_PER_USER`, specific enum strings, or pagination limits directly into the service logic.

### 4. `helpers.ts`
- **Purpose:** A catch-all for small algorithmic logic.
- **Usage:** Might contain logic for sanitizing Markdown generated by the AI, generating random slugs, or parsing HTTP headers.

## Suggested Improvements & Cleanup
- **Duplication Risk:** Client `validation.ts` and server `validators/` might be duplicating Zod schemas. If they define the exact same `projectSchema`, this is duplicate code. They could be merged if the project transitions to a monorepo structure (e.g., Turborepo with a shared `packages/common` folder).
